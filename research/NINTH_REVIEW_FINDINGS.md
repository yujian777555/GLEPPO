## R46 — Approval record has no trusted authorization source (BLOCKER)

**Evidence:**
- `gleppo/pc1.py:PlannerApprovalRecord.validate()` validates caller-provided fields and a hash, but does not verify a signature, trusted approval artifact, authenticated Planner decision, or protected approval event.
- `ApprovalGate.check()` reads the current protocol document and checks that its status equals `APPROVED`; if the document were changed to APPROVED, a caller could construct a new arbitrary `PlannerApprovalRecord` with the current document hash, invented approval ID/approver, and a valid date. No code establishes that the purported approver actually authorized the protocol.
- `ApprovalGate.expected_protocol_hash` is stored but not used in `check()`. Gate-level `approver` and `approval_date` fields are also not validated or bound to the record.
- `tests/test_r39_r42.py:test_gate_with_forged_record_rejected` tests a record with a deliberately wrong hash (`"forged"`), not an invented record with the exact current document hash. `test_valid_record_passes` calls `PlannerApprovalRecord.validate()` without `canonical_status`, so an invented APPROVED record with the current proposed document's hash passes that standalone validator.

The current status guard prevents gate passage while the document remains proposed, but it does not establish trusted authorization after the status is changed.

**Required fix:**
1. Bind approval to a trusted artifact or authenticated approval event, such as a verifiable signed approval record whose trust anchor is pinned independently of the mutable protocol document.
2. Verify approval identity, exact protocol hash/version, status, and real calendar date from that artifact; do not treat caller-supplied fields as proof.
3. Either use `expected_protocol_hash` as an independently pinned expected value or remove the misleading field and document the real trust boundary.
4. Add a test that constructs an invented approval record with the exact current protocol hash and valid date. It must fail without a trusted approval artifact.
5. Preserve default-deny behavior and keep registered PC1 execution refused.

## R47 — Plan artifact is self-hashed but not bound to the registered canonical plan (BLOCKER)

**Evidence:**
- `load_plan_artifact()` recomputes SHA-256 over the artifact's `mapping` and compares it with the artifact's own `plan_hash`.
- `run_pc1_analysis()` only compares the caller's `plan_hash` with that loaded artifact hash, then validates records against that artifact mapping.
- No check compares the loaded mapping/hash to an independently pinned registered plan identity/hash, the canonical mapping generated by `generate_plan_mapping()`, or a protocol-bound plan hash.
- `tests/test_r39_r42.py:TestR41PlanArtifact` covers ordinary round-trip, mutation without recomputing the hash, defensive copies, and a wrong hash. It does not create a structurally valid alternative mapping with a recomputed self-hash and prove that registered analysis rejects it.

An arbitrary alternative plan can therefore be made internally self-consistent by recomputing its own hash; matching that hash does not prove it is the registered plan.

**Required fix:**
1. Define a stable registered plan identity/version and independently pin its canonical hash (or bind it to an approved protocol/manifest artifact).
2. Require `load_plan_artifact()` and registered analysis to compare the loaded artifact to that registered identity/hash, not just the hash stored inside the same artifact.
3. Store plan identity, version, and canonical hash in raw evidence.
4. Add an end-to-end negative test that changes the mapping, recomputes the artifact's own hash, supplies that matching hash, and confirms registered analysis still rejects the noncanonical plan.
5. Keep Family C excluded.

## R48 — Protocol semantic checks still accept materially changed contracts (BLOCKER)

**Evidence:** `gleppo/pc1.py:protocol_consistency_check()`, lines 152–190:
- Reward clipping and coefficients are checked by substring inclusion (for example `"0.1" in reward`, `"0.25" in reward`, `"-0.5" in reward`, `"1.0" in reward`).
- The best-reward coefficient `W_BEST` is imported but not checked against the documented formula.
- Estimator checks require selected phrases such as `"Q-rollout first"`, `"extra"`, `"discounted"`, `"q_rollout"`, and `"only"`, rather than checking an exact structured contract.
- Seed checks require fragments such as `"crn-v2"`, `"json"`, or `"typed"`; they do not prove that action/genotype are excluded or that the exact typed field schema matches implementation.

For example, a reward string that appends an additional term but retains the expected coefficients and clip values can satisfy these checks while changing the reward semantics. Similar additions to estimator or seed-contract text can pass without representing the actual implementation.

**Required fix:**
1. Replace prose-substring checks with structured protocol fields: reward contract ID, exact numeric weights and clipping bounds; estimator contract ID and sample-role semantics; seed schema version and exact field list.
2. Compare every structured value to executable constants/contract objects.
3. Add adversarial mutation tests that retain the current expected substrings but alter the reward with an extra term, change estimator weighting/horizon, or add action/genotype to the seed field list. All must fail.
4. Do not call these checks exact until such mutations are rejected.

## R49 — Protocol status is locked to PROPOSED, creating an approval-state deadlock (BLOCKER)

**Evidence:**
- `protocol_consistency_check()` hardcodes `doc.get("status") == "PROPOSED_NOT_APPROVED"` at line 163.
- `ApprovalGate.check()` requires the same canonical document's status to be exactly `"APPROVED"` through `PlannerApprovalRecord.validate()`.
- `run_pc1_analysis()` requires `protocol_consistency_check()` to pass before registered analysis.

Thus, changing the canonical protocol status to APPROVED causes the consistency check to fail, while leaving it PROPOSED causes the approval gate to reject. There is no valid canonical status that satisfies both paths as currently written. The code constant `PROTOCOL_STATUS` is also `PROPOSED_AWAITING_PLANNER_APPROVAL`, which differs from the document's `PROPOSED_NOT_APPROVED` string.

**Required fix:**
1. Model protocol lifecycle explicitly: a protocol's immutable content/version/hash should be separate from its approval state.
2. Let consistency checking validate the protocol content/version independently of lifecycle status.
3. Validate approval state through the trusted approval artifact described in R46.
4. Add transition tests for proposed/unapproved (must deny execution), approved with valid trusted record (gate may pass), and content changed after approval (must deny).
5. Do not mark the protocol approved or execute PC1 as part of this remediation.
