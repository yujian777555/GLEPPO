## R50 — Trusted approval artifact is disconnected from the actual gate, and its check is not cryptographic (BLOCKER)

**Evidence:**
- `gleppo/pc1.py` defines `TrustedApprovalArtifact.verify()`, but `ApprovalGate` has no `TrustedApprovalArtifact` field and does not call `verify()`. `ApprovalGate.check()` still validates only `PlannerApprovalRecord`.
- Repository tests do not import or reference `TrustedApprovalArtifact` or `approval_secret_hash`. The existing `test_gate_with_forged_record_rejected` uses a deliberately wrong hash, so it does not prove that a forged record with the exact canonical hash is rejected after the protocol is approved.
- `TrustedApprovalArtifact.verify()` accepts `pinned_secret_hash` as a method argument and merely compares it with the artifact's `approval_secret_hash` field. There is no signature/MAC over the approval fields and no independently configured trust anchor or trusted artifact loader in the reviewed source. A caller able to construct the artifact can copy a known hash into the field; matching a public hash does not authenticate the approver or the approval event.
- The old `PlannerApprovalRecord.validate()` remains the active gate path. If the canonical protocol status is changed to APPROVED, the old record can still be constructed from caller-supplied fields unless the gate is changed to require the trusted path.

**Required fix:**
1. Wire trusted approval verification directly into `ApprovalGate.check()`; the gate must not accept the legacy caller-populated record as sufficient authorization.
2. Use an actual verifiable approval artifact: for example, a signature over canonical approval fields, verified using a public key pinned outside the mutable protocol document/repository-controlled approval data. Do not generate a private key or fabricate an approval in this remediation.
3. Bind artifact ID, approver identity, approval date, immutable protocol-content hash and version into the signed payload; verify date and identity policy.
4. Add tests proving that a forged artifact with the correct protocol hash, copied trust-anchor hash, altered approver, altered date, or altered protocol hash is rejected unless the signature is valid.
5. Add a gate-level test demonstrating that the trusted artifact is actually consumed by the gate.

## R51 — Registered plan hash is not independently pinned; plan identity/version are unused (BLOCKER)

**Evidence:**
- `get_registered_plan_hash()` lazily computes `_CANONICAL_PLAN_HASH` by calling `generate_plan_mapping()` in the same runtime. This is a generated reference hash, not an independently pinned constant or externally approved manifest value.
- `REGISTERED_PLAN_ID` and `REGISTERED_PLAN_VERSION` are declared but are not stored in or verified against the plan artifact.
- `load_plan_artifact()` checks the embedded self-hash and compares it to the runtime-generated hash. It does not validate an explicit artifact ID/version.
- `TestR41PlanArtifact` tests round-trip, tampering without recomputing the hash, defensive copying, and a wrong hash. It does not construct a different, structurally valid mapping, recompute that mapping's hash, and verify rejection against an independently pinned registered plan identity.

**Required fix:**
1. Define a canonical registered plan artifact identity/version and pin its full canonical hash independently, e.g. through a versioned and review-approved manifest whose identity is itself verified.
2. Include plan ID, version, mapping hash and protocol-content hash in the artifact/evidence; verify all of them at the registered analysis boundary.
3. Add an end-to-end test that changes a valid mapping and recomputes its own hash; the noncanonical plan must still be rejected.
4. Do not describe a hash recomputed from the same generator as independently pinned.

## R52 — Structured protocol semantic validation is incomplete (BLOCKER)

**Evidence:**
- The reward contract checks individual known keys but does not require an exact schema or reject unknown keys. An extra semantic field can be added while all existing checks continue to pass.
- The estimator contract checks horizon, gamma, `r_hat_sources`, and `q_hat_role`, but does not enforce an exact contract/schema or reject unknown keys.
- The seed check validates the expected field list and excludes `action`/`genotype`, but does not check `seed_schema.version` or `seed_schema.encoding` against the implementation. Changing `version` or `encoding` while retaining the current fields can still pass.
- The current tests cover a wrong `w_best` value and a seed field list containing action/genotype, but do not cover altered seed version/encoding, extra reward-contract keys/terms, or adversarial estimator-contract additions. The claimed extra-term and estimator mutation coverage is not present in the inspected test source.

**Required fix:**
1. Validate exact typed contract objects or explicit allow-listed schemas; reject unknown/missing keys.
2. Compare seed version and encoding with the executable seed implementation, not only the fields.
3. Add adversarial mutation tests for wrong seed version, wrong encoding, extra reward terms/keys, extra estimator semantics/keys, missing keys, and wrong types.
4. Ensure the tests fail when a contract changes while preserving the expected existing values.

## R53 — Lifecycle status is still included in the protocol hash (BLOCKER)

**Evidence:**
- `compute_protocol_hash(doc)` serializes and hashes the entire parsed JSON dictionary, including `status`.
- The protocol JSON block still contains `"status": "PROPOSED_NOT_APPROVED"`.
- `TestR40ProtocolConsistency.test_mutation_status_not_checked_by_consistency` proves only that status changes do not fail the content checker. It does not prove that the status is excluded from the content hash.
- Consequently, changing status from PROPOSED to APPROVED changes the hash used by the approval record. The implementation has separated status from the consistency predicate, but it has not fully separated lifecycle state from immutable protocol-content identity as claimed.

**Required fix:**
1. Define a canonical immutable protocol-content payload/hash that excludes lifecycle status and approval metadata.
2. Store lifecycle status and approval evidence separately, and bind approval to the immutable content hash/version.
3. Add a test proving that changing only lifecycle status leaves the immutable content hash unchanged, while changing any decision-critical protocol field changes it.
4. Keep PROPOSED / NOT APPROVED until a real, trusted Planner approval occurs.
